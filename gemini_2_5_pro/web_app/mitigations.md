| Threat Type | Scenario | Suggested Mitigation(s) |
| :--- | :--- | :--- |
| Spoofing | An attacker intercepts a user's session ID after they log in. Since the Web Service uses this ID for session management, the attacker can replay this ID to the Web Service to gain access as the legitimate user. | 1. Enforce TLS: Encrypt all traffic between the Web UI and the Web Service using a strong TLS 1.2+ configuration to prevent interception.<br>2. Secure Session Cookie Attributes: Set the `HttpOnly` flag on the session cookie to prevent access by client-side scripts, and the `Secure` flag to ensure it is only transmitted over HTTPS.<br>3. Session ID Regeneration: Generate a new, cryptographically random session ID for the user immediately after a successful login to invalidate any pre-login session ID. |
| Spoofing | An attacker creates a phishing website that perfectly mimics the Web UI. A user is tricked into entering their username and password, which the attacker captures and uses to log into the real application. | 1. Implement Multi-Factor Authentication (MFA): This is the most effective control. Require a second factor (e.g., TOTP authenticator app, hardware key) for login, so a stolen password alone is insufficient for access.<br>2. User Education: Conduct regular security awareness training to help users identify phishing attempts (e.g., checking URLs, recognizing social engineering tactics).<br>3. Implement DMARC/DKIM/SPF: Configure these email authentication standards to prevent attackers from spoofing your domain in phishing emails, making them less likely to reach users' inboxes. |
| Spoofing | If the Web Service's XML parser is misconfigured to trust external entities and the Web UI-to-Web Service connection is not properly secured, an attacker could spoof internal server requests (SSRF) via a malicious XML payload. | 1. Secure XML Parser Configuration: Disable external entity processing in the Java XML parser. Set features like `http://apache.org/xml/features/disallow-doctype-decl` to `true` to prevent XXE-based SSRF.<br>2. Egress Filtering with Security Groups: Configure the EC2 instance's AWS Security Group to deny all outbound traffic by default, and only allow connections to specific, required internal services (like the RDS database endpoint) on the necessary ports.<br>3. Use IAM Roles for EC2: Assign a least-privilege IAM role to the EC2 instance. Even if an SSRF attack is successful, the temporary credentials obtained will have minimal permissions, preventing broad discovery or interaction with other AWS services. |
| Tampering | An attacker injects a malicious XML payload into a request sent to the Web Service. The payload is crafted as an XML External Entity (XXE) injection, designed to alter data or execute unauthorized commands on the underlying EC2 instance. | 1. Disable XXE Processing: The primary mitigation is to configure the Java XML parser to completely disable DTDs and external entities. This neutralizes the XXE vulnerability at its source.<br>2. Principle of Least Privilege: Run the Web Service application on the EC2 instance using a dedicated, non-root user account with minimal file system permissions. This contains the impact of a code execution exploit.<br>3. Least-Privilege Database User: Ensure the database connection used by the Web Service has only the necessary `SELECT`, `INSERT`, `UPDATE`, `DELETE` permissions on specific application tables, preventing unauthorized schema changes or privilege escalation within the database. |
| Tampering | A malicious user manipulates data within their client-side session (e.g., in hidden form fields or parameters in a JQuery-driven request) to reference another user's ID or resources before submitting it to the Web Service. | 1. Implement Server-Side Authorization Checks (IDOR Prevention): This is critical. For every request, the Web Service must verify that the authenticated user (from their server-side session) is authorized to access or modify the requested resource. Never trust user-provided IDs for authorization.<br>2. Use Indirect Object References: Avoid using direct database identifiers (e.g., `id=123`) in API calls. Instead, use per-user indirect references (e.g., UUIDs) that are mapped to the actual database ID on the server, making it impossible to guess other users' resource IDs. |
| Tampering | An attacker with access to the EC2 instance hosting the Web Service tampers with the application's configuration files to alter the database connection string, pointing it to a malicious database to skim data. | 1. Use AWS Secrets Manager: Do not store the database connection string or credentials in a configuration file. Instead, store them in AWS Secrets Manager or Parameter Store and use an IAM Role attached to the EC2 instance to grant the application permission to retrieve them at runtime.<br>2. File Integrity Monitoring (FIM): Deploy a FIM solution (like AWS Inspector or a third-party agent) to monitor critical configuration files for unauthorized changes and generate immediate alerts.<br>3. Immutable Infrastructure: Adopt an immutable infrastructure approach where instances are never modified after deployment. To update configuration, a new, patched instance is deployed to replace the old one. |
| Repudiation | A legitimate user modifies sensitive customer PII through the Web UI and later denies making the change. The system lacks detailed, immutable audit logs connecting the user's session ID to the specific database transaction. | 1. Implement Comprehensive Audit Logging: For every sensitive transaction, log the authenticated user ID, session ID, source IP, timestamp, action performed, and the "before" and "after" state of the modified data.<br>2. Use Append-Only, Secure Log Storage: Send application logs to a secure, write-once service like Amazon CloudWatch Logs. Configure IAM policies and resource-based policies to prevent log modification or deletion. For long-term retention, archive logs to an S3 bucket with Object Lock enabled. |
| Repudiation | An attacker uses a compromised account to exfiltrate data. Due to insufficient logging of data access patterns (e.g., which records were viewed, by whom, and when), the organization cannot prove what specific data was stolen. | 1. Log All Data Access Events: In addition to modification logs, audit logs must include `READ` events for all sensitive PII. Log which user viewed which specific customer record and when.<br>2. Enable Database-Level Auditing: Configure the PostgreSQL RDS instance with an extension like `pgaudit` to create a separate, low-level audit trail of all queries executed against sensitive tables.<br>3. Implement Threat Detection: Use services like Amazon GuardDuty to detect anomalous activity (e.g., unusual data access volumes, access from suspicious IPs) and correlate it with application logs in a SIEM to identify potential breaches in real-time. |
| Information Disclosure | An attacker exploits an XML External Entity (XXE) vulnerability in the Web Service's XML parser to read sensitive files from the EC2 instance's file system, such as application configuration files containing PostgreSQL database credentials. | 1. Disable XXE and Externalize Secrets: Combine two key mitigations. First, disable XXE in the parser to block the attack vector. Second, remove the target by storing database credentials in AWS Secrets Manager instead of a local file, so there is no sensitive file to read.<br>2. Apply File System Least Privilege: Ensure the application's service account has read/write access only to its necessary directories and cannot read system-level configuration files or other users' home directories. |
| Information Disclosure | The Java Web Service returns a detailed stack trace in an error message to the client. This error reveals the specific version of the Java container, internal file paths, and database schema information. | 1. Implement Global Exception Handling: Configure the application framework to catch all unhandled exceptions.<br>2. Return Generic Error Messages: The global handler should return a generic, non-descriptive error message to the user (e.g., "An error occurred. Please contact support and provide reference ID: [unique-id]").<br>3. Log Detailed Errors Server-Side: Log the full, detailed stack trace along with the unique reference ID to a secure, server-side log aggregator like CloudWatch Logs for debugging by authorized personnel. |
| Information Disclosure | A user's session ID is passed in the URL. This ID is leaked to third parties via the Referer header when the user clicks an external link, or is stored in browser history, proxy logs, or server logs. | 1. Use Cookies for Session IDs: Store session IDs exclusively in browser cookies. Never transmit them in URL query parameters.<br>2. Implement Secure Cookie Flags: As previously mentioned, set the `Secure`, `HttpOnly`, and `SameSite=Lax` or `SameSite=Strict` attributes on the session cookie to protect it from interception, client-side script access, and cross-site request leakage. |
| Denial of Service | An attacker sends a specially crafted XML document, known as an 'XML Bomb' or 'Billion Laughs Attack', to the Web Service. The parser attempts to process the nested entities, consuming all available CPU and memory on the EC2 instance. | 1. Disable DTD Processing: The most effective mitigation is to configure the XML parser to disallow Document Type Definitions (DTDs) entirely, as these attacks rely on entity expansion defined in a DTD.<br>2. Use a Web Application Firewall (WAF): Configure AWS WAF with rules to inspect request bodies and block requests containing suspicious XML entity patterns or excessively large payloads before they reach the EC2 instance.<br>3. Resource Limits: If DTDs cannot be disabled, configure the parser with strict limits on entity expansion depth and the total number of entity expansions. |
| Denial of Service | An attacker initiates a large number of concurrent connections and sessions with the Web Service. If session lifecycle and resource pooling are not properly managed, the service exhausts available memory or database connections. | 1. Rate-Based Blocking with AWS WAF: Implement rate-based rules in AWS WAF to automatically block IP addresses that exceed a configured request threshold (e.g., 2000 requests in 5 minutes).<br>2. Implement Auto Scaling: Configure an AWS Auto Scaling group for the EC2 instances. Set scaling policies based on metrics like average CPU utilization or network traffic to automatically add capacity during a traffic surge.<br>3. Tune Connection Pools: Properly configure the maximum size and timeout settings for the web server's thread pool and the application's database connection pool (e.g., HikariCP) to prevent resource exhaustion. |
| Denial of Service | An attacker repeatedly submits requests for a computationally expensive operation via the Web UI (e.g., a complex search or report generation), causing the Web Service and PostgreSQL database to be overloaded. | 1. Apply Endpoint-Specific Rate Limiting: Use AWS WAF or application-level logic to apply stricter rate limits to known expensive API endpoints.<br>2. Offload Long-Running Tasks: Redesign computationally expensive operations to be asynchronous. The initial API call should queue a background job and return a job ID immediately, preventing the web server thread from being tied up. The user can poll a status endpoint for the result.<br>3. Database Query Optimization: Ensure complex search queries are backed by appropriate indexes in the PostgreSQL database. Analyze query plans using `EXPLAIN ANALYZE` to identify and fix performance bottlenecks. Enforce pagination on all search results. |
| Elevation of Privilege | A low-privilege user finds a Cross-Site Scripting (XSS) vulnerability in the JQuery Web UI. They craft a malicious link and send it to an administrator. When the administrator clicks it, the injected script steals their session ID, allowing the attacker to hijack the admin's session. | 1. Set `HttpOnly` Cookie Flag: This is the most direct mitigation. By making the session cookie inaccessible to JavaScript, the attacker's script cannot steal it, even if an XSS vulnerability exists.<br>2. Enforce Context-Aware Output Encoding: The primary fix for XSS is to encode all user-supplied data on output, specific to its context (HTML, JavaScript, CSS). Use a standard library like the OWASP Java Encoder.<br>3. Content Security Policy (CSP): Implement a strict CSP header to prevent the execution of inline scripts and restrict script sources to trusted domains, severely limiting the impact of any potential XSS flaw. |
| Elevation of Privilege | The Web Service connects to the PostgreSQL database using an account with excessive permissions (e.g., 'postgres' superuser). An attacker who compromises the Web Service can now use these credentials to perform administrative actions on the database. | 1. Enforce Principle of Least Privilege on Database User: Create a dedicated database role for the application with the absolute minimum permissions required. It should only have `CRUD` (Create, Read, Update, Delete) access on the specific tables it manages, and nothing more. It should not be able to alter the schema or manage users.<br>2. Use RDS IAM Database Authentication: Instead of using password-based authentication, configure the RDS instance and the application to use IAM for authentication. This ties database access permissions to the EC2 instance's IAM role, centralizing access control and eliminating long-lived database passwords. |
| Elevation of Privilege | An authenticated user discovers that API endpoints on the Web Service do not perform authorization checks to verify that the user is the owner of the data they are requesting. The user modifies an API request to include another user's ID, successfully accessing their data. | 1. Mandate Authorization Checks on Every Request: This is the same critical control for the related Tampering threat. The Web Service logic for every relevant API endpoint must retrieve the user's identity from the trusted server-side session and verify that this identity has ownership or permission to access the specific data record being requested.<br>2. Centralize and Test Authorization Logic: Implement these authorization checks in a shared, reusable component (e.g., a filter, middleware, or AOP aspect) that is applied consistently. Create specific, automated tests that attempt to access resources belonging to other users and assert that the requests are denied with a `403 Forbidden` or `404 Not Found` status. |
