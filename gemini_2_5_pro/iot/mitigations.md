| Threat Type | Scenario | Suggested Mitigation(s) |
| --- | --- | --- |
| Spoofing | An attacker on the same 'public access LAN' as the IoT Edge device could impersonate the M1 module. By using techniques like ARP spoofing, the attacker can intercept the initial connection from the user's browser, presenting a fake web application to steal credentials or inject malicious scripts. | - Implement HTTPS (TLS): Configure the web server in the M1 module to serve its content exclusively over HTTPS (`https://`). This requires provisioning a TLS certificate for the module's endpoint.<br>- Use Trusted Certificates: The TLS certificate used by M1 must be issued by a Certificate Authority (CA) that is trusted by default in users' browsers. Avoid self-signed certificates, which train users to ignore security warnings.<br>- Network-Level Controls: As a defense-in-depth measure, deploy network infrastructure (switches) that support and have Dynamic ARP Inspection (DAI) enabled to prevent ARP spoofing attacks on the LAN. |
| Spoofing | An attacker on the 'public access LAN' can send crafted WebSocket messages to M2 or M3, pretending to be a legitimate upstream module (e.g., spoofing M1 to M2). This could be used to inject malicious or fabricated data into the processing pipeline. | - Implement Mutual TLS (mTLS): Require all inter-module communications to use mTLS. Each module must possess a unique client certificate, and downstream modules (M2, M3) must be configured to validate this certificate and only accept connections from modules presenting a trusted certificate. This provides strong, two-way authentication.<br>- Use Secure WebSockets (WSS): All inter-module communication must use the `wss://` protocol to ensure a TLS-encrypted and authenticated channel. |
| Spoofing | An attacker on the IoT Edge device's network path to the internet could use DNS spoofing to redirect requests for Azure Cognitive Services to a malicious server. The malicious server could then capture the connection string from the request headers. | - Rely on Standard TLS Certificate Validation: The Azure SDKs inherently use HTTPS, which validates the server's certificate against a trusted root CA store. This process naturally defeats simple DNS spoofing as the attacker's server will not have a valid certificate for `*.cognitiveservices.azure.com`.<br>- Harden Host DNS Resolution: Configure the IoT Edge host OS to use encrypted DNS protocols like DNS-over-HTTPS (DoH) or DNS-over-TLS (DoT). This encrypts DNS queries, preventing them from being intercepted or spoofed by a network attacker. |
| Tampering | Since modules communicate via WebSockets on a public access LAN, an attacker can perform a Man-in-the-Middle (MITM) attack to intercept and alter the data flowing between M1, M2, and M3. For example, they could modify the video frames in transit. | - Enforce Secure WebSockets (WSS): Mandate the use of `wss://` for all WebSocket connections between modules. The underlying TLS protocol provides data integrity through Message Authentication Codes (MACs), which guarantees that any modification to the data in transit will be detected, causing the connection to be dropped. |
| Tampering | An attacker with access to the IoT Edge device's local storage could modify the container images for M1, M2, or M3 that were deployed by the CI/CD pipeline. The next time the module starts, it will run the attacker's tampered code. | - Implement Image Signing: Integrate Docker Content Trust (Notary) into your CI/CD pipeline to cryptographically sign all container images. Configure the IoT Edge runtime on the device to enforce signature verification, ensuring it will only pull and run images that have a valid signature from your trusted registry.<br>- Harden Host OS Storage: Employ host-level security controls such as full disk encryption (e.g., LUKS, BitLocker), secure boot, and restrictive file system permissions (e.g., using SELinux/AppArmor) to prevent unauthorized access and modification of the container image storage directory (`/var/lib/docker` or equivalent). |
| Tampering | An attacker who has obtained the connection string for the Azure Storage account can directly connect to it and modify or delete the 'feedback frames' uploaded by M2 for debugging purposes. | - Use Managed Identity and RBAC: The most secure method. Use an Azure AD Managed Identity for the IoT Edge device. Grant this identity a granular RBAC role (e.g., "Storage Blob Data Contributor") scoped specifically to the 'feedback frames' container, not the entire storage account. This eliminates the connection string entirely.<br>- Implement Least-Privilege SAS Tokens: If Managed Identity is not viable, generate short-lived Shared Access Signature (SAS) tokens with write-only permissions scoped to the specific target container. The module should request a new token periodically.<br>- Enable Blob Soft Delete: Enable the soft delete feature on the Azure Storage account. This allows for the recovery of blobs that an attacker might delete, preserving critical debug data. |
| Repudiation | The system sends telemetry to Application Insights. An attacker who has compromised a module on the device could stop it from sending telemetry before performing malicious actions, leaving no trace in the logs. | - Implement Heartbeat Monitoring: Each module should emit a periodic "I'm alive" heartbeat signal to Azure Monitor. Configure an alert rule that triggers if a device's heartbeat is missing for a predefined interval, indicating a potential compromise or failure.<br>- Leverage IoT Edge Runtime Logs: Ensure the IoT Edge runtime's own logs (which record module start/stop events) are being collected and sent to a secure, centralized log workspace. An attacker within a container cannot easily suppress these external logs.<br>- Deploy Azure Defender for IoT: Install the security module for Azure Defender for IoT on the device. It provides threat detection for the IoT Edge device and modules, including alerts for events like unexpected module termination. |
| Repudiation | An attacker or malicious user can submit a video stream for processing that triggers an undesirable outcome. Without strong, verifiable audit logs tying the browser session (via SSO identity) to the specific requests made, the user could plausibly deny they submitted the content. | - Enforce User Authentication: Require all users to authenticate to the M1 web application via a robust identity provider (e.g., Azure AD B2C) before they can submit any data. Anonymous access should be disabled.<br>- Implement End-to-End Auditing with Correlation IDs: Upon authentication, generate a unique correlation ID. This ID, along with the authenticated user's identifier, must be injected into the data stream and logged by every module (M1, M2, M3) as it processes the request. All audit entries must be sent to a tamper-evident, centralized logging service. |
| Information Disclosure | The connection strings for Azure services are stored on the IoT Edge device. An attacker who gains even low-privileged access to the device's filesystem or is able to read process environment variables could steal these connection strings. | - Use Azure Key Vault with Managed Identity: Store all secrets in Azure Key Vault. Grant the device's Managed Identity access to retrieve these secrets. The modules can then fetch secrets directly from Key Vault at runtime, removing them from the deployment manifest and device storage.<br>- Leverage the IoT Edge HSM/TPM: Utilize the IoT Edge security daemon's ability to encrypt secrets using a hardware-backed key stored in a Trusted Platform Module (TPM). The secrets are decrypted by the security daemon in memory and passed to modules, never resting in plain text on the file system.<br>- Adopt Managed Identity for all Azure Services: The preferred solution is to completely eliminate connection strings. Use the device's Managed Identity and grant it RBAC roles on the target Azure resources (Storage, Cognitive Services, etc.). |
| Information Disclosure | The WebSocket communication between M1, M2, and M3 on the 'public access LAN' may not be encrypted (i.e., using `ws://` instead of `wss://`). An attacker on the LAN can passively sniff this traffic and capture the raw video frames and OCR results. | - Mandate Secure WebSockets (WSS): All inter-module communication must use the `wss://` protocol. This wraps the WebSocket traffic in TLS, providing strong encryption that prevents any network eavesdropper from viewing the confidential data being transmitted between modules. |
| Information Disclosure | An attacker on the 'public access LAN' can directly connect to the HTTP endpoints of M1, M2, M3... If these endpoints have verbose error messages or unauthenticated status pages, they could leak internal system information. | - Minimize Attack Surface: Disable or remove any diagnostic or management HTTP endpoints that are not essential for operation. All remaining endpoints must require authentication (e.g., mTLS).<br>- Configure Generic Error Responses: Configure all module web servers to suppress detailed error information (e.g., stack traces, software versions) in HTTP responses. This information should only be written to secure backend logs.<br>- Remove Server Banners: Configure web servers to not send identifying banners like `Server: nginx/1.21.0` in HTTP headers. |
| Denial of Service | An attacker on the 'public access LAN' can send a high volume of HTTP requests or WebSocket connections to the M1 module. This would overwhelm its resources, preventing legitimate users from accessing the web application. | - Implement Rate Limiting: Apply rate limiting to M1's public-facing endpoints based on source IP address and/or authenticated user ID. This throttles abusive clients and preserves resources for legitimate users.<br>- Set Resource Quotas for Containers: In the IoT Edge deployment manifest, define strict CPU and memory limits for each module's container. This prevents a targeted module from consuming all host resources and impacting the stability of the entire device. |
| Denial of Service | An attacker who has stolen an Azure connection string (e.g., for Cognitive Services) can run a script to make an unlimited number of API calls. This will rapidly consume the service's monthly quota or incur a very large bill. | - Set Billing Alerts: Configure budget alerts in Azure Cost Management to send notifications when spending on the service or subscription exceeds a defined threshold. This provides early detection of financial abuse.<br>- Use Quota-Limited Service Tiers: Select a pricing tier for the Azure service that has built-in rate or transaction limits that align with expected legitimate usage.<br>- Eliminate Persistent Secrets: Prioritize the use of Managed Identity or short-lived, narrowly-scoped SAS tokens over static connection strings. This drastically reduces the window of opportunity for an attacker to abuse a stolen credential. |
| Denial of Service | An attacker with physical access to the IoT Edge device could simply disconnect the USB Video Camera, or an attacker with root access on the device OS could disable the USB port. | - Implement Physical Security: Place the IoT Edge device inside a locked, tamper-resistant enclosure that physically protects I/O ports, power, and network connections.<br>- Implement Health Monitoring and Alerting: The M1 module must continuously monitor the status of its video source. If the camera stream is lost for a specified duration, it must generate a high-priority alert in the central monitoring system (Azure Monitor) to notify operators of the service disruption. |
| Elevation of Privilege | A vulnerability, such as a buffer overflow or command injection flaw, in the M1 module's HTTP endpoint could be exploited by an attacker... leading to remote code execution within the M1 container. | - Follow Secure Software Development Lifecycle (SDL): Implement a rigorous SDL that includes mandatory secure coding training, use of static analysis (SAST) and dynamic analysis (DAST) security tools in the CI/CD pipeline, and peer review of security-sensitive code.<br>- Scan for Vulnerable Dependencies: Continuously scan all third-party libraries and base container images for known vulnerabilities (CVEs) and have a process to patch them promptly. |
| Elevation of Privilege | An attacker who has achieved code execution inside a module container... can attempt a 'container escape' attack... and gain root access to the host IoT Edge device OS. | - Run Containers as a Non-Root User: This is the single most important mitigation. Define a dedicated, unprivileged user in the `Dockerfile` and use the `USER` directive to ensure the application process does not run as root.<br>- Apply Least Privilege Container Configuration: In the `createOptions` of the deployment manifest, explicitly drop all unnecessary Linux capabilities, run with a read-only root filesystem, disable privileged mode (`"Privileged": false`), and apply a restrictive seccomp security profile.<br>- Maintain Host and Runtime Patching: Keep the host OS kernel and the Moby container runtime fully patched to mitigate known container escape vulnerabilities. |
| Elevation of Privilege | An attacker compromises the IoT Edge device and steals the Azure Storage connection string. This string grants them high-level permissions on the storage account itself... | - Enforce Principle of Least Privilege via Scoping: The core issue is an overly permissive credential. Replace the account-level key with a credential that is scoped to the minimum required resource. Use either:<br>    1. A SAS token granting write-only access to a single blob container.<br>    2. Managed Identity with an RBAC role assignment granting write access to that same single container.<br>This ensures that a compromise of the device does not grant the attacker access to any other data or resources in the storage account. |
