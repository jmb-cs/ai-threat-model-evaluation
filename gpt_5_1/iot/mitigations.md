| Threat Type | Scenario | Suggested Mitigation(s) |
|-------------|----------|-------------------------|
| Spoofing | An attacker on the same LAN as the IoT Edge device and Browser captures or reuses SSO authentication artifacts (e.g., tokens, cookies) from a user’s Browser session to M1’s HTTP endpoint, then sends their own requests to M1 pretending to be that user. | - Enforce HTTPS/TLS for all Browser↔M1 traffic (including WebSocket upgrades), with HSTS and modern ciphers to prevent credential capture via sniffing.<br>- Use secure cookies for session/SSO artifacts: `HttpOnly`, `Secure`, `SameSite=Strict/Lax`; never pass tokens in URLs or localStorage if avoidable.<br>- Prefer OAuth2/OIDC Authorization Code + PKCE against the IdP; M1 should receive only short-lived, audience-bound tokens and exchange them for internal session tokens.<br>- Implement replay resistance: bind sessions to client attributes (e.g., device fingerprint, IP range) and invalidate on unusual changes; use short token lifetimes and refresh tokens with server-side revocation lists.<br>- Implement CSRF protection for state‑changing operations (anti-CSRF tokens, SameSite cookies) to limit token misuse through browser-based attacks.<br>- Segment the network so M1 is not exposed on open WLANs; use VLANs/Wi-Fi security (WPA2-Enterprise/WPA3) and restrict LAN access to authorized devices only.<br>- Continuous monitoring and anomaly detection on M1 to flag abnormal usage patterns (e.g., one identity issuing many OCR/TTS requests from multiple IPs). |
| Spoofing | A malicious process on the IoT Edge device or another device on the LAN impersonates M2 or M3 by opening a WebSocket endpoint that M1 connects to, if module-to-module authentication is not enforced on the WebSocket channels. | - Require mutual TLS (mTLS) for all M1↔M2↔M3 WebSocket connections, using device/module certificates managed by Azure IoT Edge so that M1 only trusts endpoints presenting valid module identities.<br>- Perform strict hostname and certificate validation (and, where feasible, certificate pinning) so that M1 only connects to known module endpoints, not arbitrary LAN addresses.<br>- Introduce application-level authentication on WebSockets (e.g., signed JWT or SAS token with module identity and scope) that M2/M3 must validate before accepting or sending data.<br>- Use Docker / IoT Edge network isolation: put M1, M2, M3 on a private internal network; only allow incoming connections from specific containers/ports; block LAN-originated connections to those ports.<br>- Whitelist expected endpoints (IP/port) for M2/M3 and have M1 refuse connections to unexpected targets; validate initial handshake with a challenge/response using shared or asymmetric keys issued by the EdgeRuntime.<br>- Log all inter-module connection attempts and failures to detect spoofing attempts. |
| Spoofing | An attacker able to influence DNS resolution or host configuration on the IoT Edge device redirects the Azure Cognitive Service hostname to an attacker-controlled HTTP endpoint that mimics the real API. | - Enforce HTTPS with strict certificate validation for all Cognitive Service calls; reject any certificate not chained to Microsoft-trusted CAs or expected hostnames.<br>- Where operationally feasible, use certificate pinning for Cognitive Service endpoints or validate known CA issuers explicitly.<br>- Lock down DNS configuration on the IoT Edge device: restrict modification of `/etc/hosts`, `resolv.conf`, and network settings to root/admin; monitor changes with file integrity monitoring (e.g., AIDE).<br>- Use trusted DNS resolvers (e.g., Azure DNS, secure corporate resolvers) and consider DNSSEC validation where supported.<br>- Prefer private endpoints / VNet integration for Cognitive Services so that traffic is routed via Azure networking, not arbitrary public DNS resolution paths.<br>- Configure the Cognitive Service base URL as read-only config mounted from a signed, version-controlled manifest; prevent runtime changes by low-privilege processes. |
| Spoofing | A malicious actor obtains an IoT Edge module’s credentials or identity (e.g., via stolen deployment credentials or misconfigured IoT Hub identities) and registers a fake IoT Edge device or EdgeRuntime that appears legitimate to Azure IoT Hub. | - Use per-device X.509 certificates or TPM-based hardware attestation with Azure IoT Hub / DPS; avoid long-lived shared keys or generic credentials.<br>- Apply strict RBAC in Azure for IoT Hub: only a small set of admin identities can create or modify device registrations; use just-in-time privileged access and MFA.<br>- Regularly rotate device/module credentials and revoke compromised identities via IoT Hub; automate rotation through policy where possible.<br>- Enable Azure Activity Logs and alerts for new device registrations, changes to device identities, or unusual patterns of registration activity.<br>- Use IoT Hub device twins and tags to validate expected properties and location of devices; alert when a “device” appears in unexpected regions or networks.<br>- For downstream systems (e.g., Application Insights consumers), perform plausibility checking on telemetry (e.g., impossible timestamps or configuration) to detect fake/rogue devices. |
| Tampering | An attacker with access to the local network or compromised module intercepts and modifies WebSocket traffic between M1, M2, and M3 (if not protected with integrity mechanisms/TLS), altering video frames or order scanning results in transit. | - Upgrade all module-to-module communication to TLS-secured WebSockets (wss://) with mutual TLS so both endpoints are authenticated and traffic is encrypted and integrity-protected.<br>- Implement application-level integrity checks (e.g., HMAC over each message using a shared secret or per-module keys) so that even if TLS is terminated upstream, tampering is detectable.<br>- Include sequence numbers and timestamps in messages to detect missing, replayed, or out-of-order video frames / scan results.<br>- Use dedicated, isolated container networks for M1/M2/M3; do not expose these channels to the broader LAN; restrict traffic via firewall rules/iptables in the host.<br>- Monitor for anomalies such as sudden changes in frame content statistics or unexpected correlations between input and OCR results that could indicate tampering. |
| Tampering | An attacker with limited access to the IoT Edge device filesystem (e.g., via another low-privileged process) modifies configuration files or environment variables that contain Azure Storage, Cognitive Service, or Application Insights connection strings. | - Store secrets in secure mechanisms rather than flat files/env vars where possible: use Azure Key Vault + managed identities, or IoT Edge module twin with encryption and in-memory retrieval only.<br>- If secrets must be on disk, store them in root-owned, read-only files with minimal permissions (e.g., `600`), and mount them into containers as read-only volumes.<br>- Run each module under a dedicated, non-root OS user; apply least-privilege filesystem ACLs so other processes cannot read or modify their configs.<br>- Make application configuration read-only at runtime (immutable config pattern) for deployed modules; require a redeploy for config changes via a controlled CI/CD path.<br>- Implement file integrity monitoring (hash-based, or use tools like AIDE/OSSEC) on configuration directories; alert on changes and maintain tamper-evident logs of who/what changed configs.<br>- Harden the host (no shell access for non-admins, disable unnecessary services, use AppArmor/SELinux profiles for containers to restrict filesystem access). |
| Tampering | A malicious insider or compromised process alters the debug data or feedback frames that M2 uploads to Azure Storage (e.g., overwriting original frames with forged ones or corrupting stored blobs). | - Enable immutable blob policies, versioning, or append-only patterns on the debug container so original frames are preserved and overwrites/deletes are either impossible or fully auditable.<br>- Use Azure RBAC instead of account keys: grant M2 write-only or append-only rights to the debug container where possible; prohibit delete/overwrite for routine module identities.<br>- Implement server-side checksums and ETags; have M2 include content hashes in metadata and verify integrity when reading frames for debugging.<br>- Log all write and delete operations in Azure Storage (Storage Analytics / Azure Monitor) and alert on unusual patterns (e.g., mass overwrites, high corruption rates).<br>- Digitally sign debug frames or frame metadata at the source module (M2) using a key not accessible to other modules; verify signatures during forensic analysis to confirm authenticity. |
| Tampering | A malicious actor tampers with telemetry sent to Azure Application Insights or Azure Monitor (e.g., by altering metric values or log contents in the sending modules) to hide abnormal behavior or fabricate normal operation. | - Use a dedicated, minimal telemetry agent (sidecar or host-level) that collects metrics/logs from modules and forwards them; limit direct write access to monitoring backends from application code where possible.<br>- Where feasible, cryptographically sign critical telemetry at the originating module with a private key stored in a secure store, and validate signatures in downstream analytics to detect tampering.<br>- Correlate Application Insights data with independent data sources (e.g., IoT Hub logs, OS logs, network device logs) to detect inconsistencies indicative of manipulation.<br>- Implement anomaly detection rules in Azure Monitor / SIEM that look for sudden telemetry “silence” or unnaturally perfect/flat metrics that may signal suppression or fabrication.<br>- Enforce RBAC on telemetry configuration so compromised modules cannot disable or redirect logging without leaving strong audit traces. |
| Repudiation | Because the Browser–M1 interaction details and audit logging are unclear, a user who initiated a set of OCR or Text-to-Speech requests later claims they never accessed certain confidential content, and there is insufficient linkage between SSO identity, session, and specific actions. | - Implement detailed, privacy-conscious audit logging on M1: log SSO identity (subject, tenant, user principal name), session ID, client IP, device details, and the specific actions (e.g., “OCR requested for frame ID X”).<br>- Use correlation IDs that propagate through M1→M2→M3 and into Cognitive Service calls, so investigators can trace a single request end-to-end.<br>- Store audit logs in a centralized, tamper-resistant service (Log Analytics / SIEM) with immutable retention policies and write-once configurations for critical audit tables.<br>- Time-synchronize all systems using NTP so timestamps are consistent across logs; this is essential for incident reconstruction and user attribution.<br>- Provide administrative tools for controlled, audited access to these logs, ensuring that they can be used as evidence in investigations while protecting sensitive payload data (e.g., log IDs instead of raw OCR text where possible). |
| Repudiation | An operator modifies IoT Edge module configurations (e.g., changes which Azure Storage account is used or toggles debug uploads) on the device, but the EdgeRuntime and modules do not log detailed, tamper-resistant configuration changes with identities and timestamps. | - Treat IoT Edge configurations as code: manage all module configurations (including debug flags, storage accounts) in a version-controlled repo with commit history, code reviews, and signed commits.<br>- Require configuration changes to be deployed via IoT Hub/CI-CD using authenticated AAD identities; disallow ad-hoc manual changes on the device in normal operations.<br>- Enable comprehensive auditing on the host OS (e.g., auditd) to record changes to configuration files, who made them, and when.<br>- Have the EdgeRuntime and/or a supervisory module log each applied configuration (hash/ID of deployment manifest, module versions, key settings) with timestamps to an append-only log store.<br>- Regularly reconcile running configs against the “source of truth” in Git/IoT Hub to detect unauthorized drift. |
| Repudiation | Deployments and updates from Azure IoT Hub to the IoT Edge device occur without detailed, immutable audit records at both ends (Hub and device) linking configuration changes to specific administrative identities. | - Use Azure AD-based authentication for all IoT Hub management operations; disable or severely restrict the use of shared access keys for deployment actions.<br>- Enable Azure Activity Logs and Diagnostic Settings for IoT Hub to stream administrative operations (e.g., deployment changes, device twin updates) to Log Analytics or a SIEM with immutable retention.<br>- Assign IoT Hub roles (e.g., IoT Hub Data Contributor) via Azure RBAC to specific admin groups; enforce MFA and just-in-time access for these roles.<br>- On the IoT Edge device, log each received deployment manifest ID, its checksum, and the time of application, and correlate that with IoT Hub activity logs.<br>- Implement a release process where deployment artifacts are signed (e.g., using GitHub Actions/DevOps signing) and the signature is verified before the EdgeRuntime accepts and applies them. |
| Repudiation | Telemetry to Application Insights and Azure Monitor is sent without strong association to specific device identities and module versions, and logs are not protected against post-hoc modification. | - Include device ID, module ID, module version, container image digest, and environment identifiers in all telemetry events and traces sent from modules.<br>- Configure Application Insights / Log Analytics with immutable, long-term retention for security-relevant tables (e.g., access logs, critical events).<br>- Limit delete/alter operations on telemetry storage via strict RBAC; disable ad-hoc editing or deletion of logs except through controlled, audited processes.<br>- Send critical security logs to an additional, independent log store or SIEM (log duplication) to prevent a single point of failure or tampering.<br>- Periodically export and archive logs to write-once storage (e.g., immutable blob containers) for long-term forensic integrity. |
| Information Disclosure | Connection strings for Azure Cognitive Service, Storage, Application Insights, and Azure Monitor—deployed from GitHub secrets to the IoT Edge device—are stored in plain text on disk or in environment variables readable by other processes on the device. | - Replace connection strings with Azure AD-based authentication and managed identities wherever possible (e.g., Storage, App Insights, Key Vault), so long-lived secrets are not distributed to the device.<br>- When connection strings are unavoidable (e.g., some Cognitive Service endpoints), store them in a secure store (Key Vault or IoT Edge’s built-in secret store) and load them into memory only at startup; avoid writing them to disk or logs.<br>- Limit environment variable visibility: run each module under a separate user and restrict tools or shells that can dump environment variables; avoid using env vars for highly sensitive secrets.<br>- Harden filesystem permissions so only root or the specific module user can read configuration files; mount secret files as read-only volumes.<br>- Set up periodic secret rotation and automate redeployment with updated secrets; assume compromise will eventually happen and limit window of misuse.<br>- Ensure CI/CD (GitHub Actions) never logs or echoes secrets; enable GitHub secret scanning and repository protection features. |
| Information Disclosure | If WebSocket connections between M1, M2, and M3 on the public-access LAN are not encrypted, an attacker with LAN access can sniff network traffic and reconstruct live video frames, OCR text, and scan results as they traverse the network. | - Enforce TLS-encrypted WebSockets (wss://) for all inter-module traffic; disable or block any unencrypted ws:// endpoints at firewall and application levels.<br>- Use mutual TLS to authenticate modules and prevent MITM sniffing or impersonation; restrict CA trust to the IoT Edge PKI where appropriate.<br>- Move inter-module communication off the public LAN onto isolated container networks or a dedicated management VLAN; block direct LAN access to these ports.<br>- Avoid including unnecessary sensitive data in messages (e.g., do not duplicate full frames when only metadata is needed; mask PII where feasible).<br>- Implement network monitoring to detect unencrypted or unexpected traffic patterns carrying video/scan data over the LAN. |
| Information Disclosure | Debug data and feedback frames uploaded by M2 to Azure Storage are stored in a container accessible using a high-privilege connection string; if the storage account or connection string is misconfigured (e.g., overly broad access or exposed in logs), external parties can list and download stored frames. | - Use separate storage accounts/containers and separate credentials for debug data, with least-privilege access (e.g., container-scoped rights only).<br>- Prefer Azure AD + RBAC for Storage access; assign M2 a role with minimal permissions (e.g., `Storage Blob Data Contributor` limited to the debug container), and avoid distributing account keys to modules.<br>- If SAS tokens are used, ensure they are short-lived, scoped to the specific container/path, and with minimal permissions (e.g., write-only for uploading; list/read only for authorized debugging tools).<br>- Disable public access to Storage containers and use private endpoints / firewall rules to restrict access to trusted networks only.<br>- Enable Access Logs / Storage Analytics and regularly review for unusual access (e.g., mass listing or download from unexpected IPs).<br>- Classify debug data as sensitive; apply encryption at rest (default) and enforce strict RBAC on human access via Azure Portal or scripts. |
| Information Disclosure | Telemetry sent to Application Insights and Azure Monitor may include sensitive content (e.g., snippets of OCR results, partial video frame data, or identifiers) and is accessible to a broad set of Azure subscribers or administrators within the tenant without strict role separation. | - Apply data minimization: review telemetry schema and strip or tokenize sensitive content (e.g., hash identifiers, truncate OCR text, avoid raw frame bits) before sending it to Application Insights/Monitor.<br>- Use separate Application Insights / Log Analytics workspaces for sensitive vs. non-sensitive telemetry; restrict access to the sensitive workspace to a small, vetted group via RBAC.<br>- Implement role-based access policies and Azure PIM (Privileged Identity Management) so only on-call or approved personnel can temporarily access sensitive telemetry with full auditing.<br>- Where sensitive data must be logged, consider additional application-layer encryption of specific fields, with keys accessible only to an incident-response group.<br>- Regularly review who has access to these monitoring resources and remove unnecessary permissions. |
| Denial of Service | An attacker on the local network sends a flood of HTTP requests to M1’s public-access LAN endpoint from multiple machines, exhausting CPU, memory, or network resources on the IoT Edge device. | - Place M1 behind a lightweight reverse proxy or API gateway with built-in rate limiting, connection throttling, and per-IP/identity quotas.<br>- Implement application-level rate limiting and backpressure in M1 (e.g., reject or defer requests once concurrency thresholds are reached) to preserve some capacity for legitimate users.<br>- Use network-level protections: host firewall rules, local WAF on the gateway, and segmentation so that only specific subnets or devices can reach M1’s endpoint.<br>- Introduce separate priority queues for critical operations so low-priority traffic cannot starve essential processing.<br>- Monitor request volumes and patterns; automatically block or blacklist IPs exhibiting clear DoS behavior, while ensuring whitelists for key operational systems. |
| Denial of Service | A malicious or compromised Browser repeatedly triggers intensive OCR and Text-to-Speech requests via M1/M2/M3 to Azure Cognitive Service, intentionally driving the service beyond its rate or quota limits. | - Implement per-user, per-session, and per-device quotas for OCR and TTS operations in M1; reject requests that exceed configured thresholds within a given time window.<br>- Enforce role-based access control: reserve high-volume operations for specific roles (e.g., “Operator”), and limit standard users to lower rates.<br>- Introduce a job/queue model where OCR/TTS requests are queued and processed at a controlled rate; apply prioritization and global rate-limits to stay under Cognitive Service quotas.<br>- Configure separate Cognitive Service resources for critical workloads vs. best-effort/debug workloads to contain abuse impact.<br>- Monitor Cognitive Service usage and set alerts on approaching quota or unusual spikes; automatically throttle or temporarily suspend suspicious identities triggering excessive requests. |
| Denial of Service | A bug or malicious logic in M2 causes massive uploads of feedback frames to Azure Storage (e.g., an infinite loop writing large blobs), exhausting storage capacity or hitting request-rate limits. | - Implement strong local safeguards in M2: cap the upload frequency, total daily bytes, and maximum blob size for debug frames; enforce backoff/retry limits and global ceilings.<br>- Add runtime controls (feature flags/configs) allowing operators to remotely disable or reduce debug uploads without redeploying the module.<br>- Use Azure Storage lifecycle management to automatically delete or tier older debug data, keeping capacity under control.<br>- Configure Storage account-level alerts for rapid growth in data volume, request rates, or egress; trigger automated workflows to pause debug uploads if thresholds are crossed.<br>- Separate debug storage from critical production storage so that a runaway debug loop does not impact other applications’ storage operations. |
| Denial of Service | An attacker who gains partial control over IoT Hub configuration sends frequent, large deployment updates or restarts to the IoT Edge device’s modules (M1, M2, M3, EdgeRuntime), forcing constant restarts. | - Apply strict RBAC and PIM for IoT Hub configuration roles; restrict deployment and device twin modification permissions to a minimal, audited set of administrators.<br>- Use CI/CD pipelines for deployments with approval gates and change management; disallow direct manual deployment changes in production IoT Hubs where possible.<br>- Monitor IoT Hub for frequent deployment updates or module restarts; alert and auto-escalate when thresholds are exceeded.<br>- Consider implementing safeguards in the EdgeRuntime or supervisory module to reject deployments that occur more often than a configured maximum frequency, or to require manual confirmation after repeated failures.<br>- Separate management IoT Hubs / subscriptions for testing vs. production to limit the blast radius of misconfigurations or malicious changes. |
| Elevation of Privilege | A vulnerability in one of the IoT Edge modules (e.g., M1’s web application) allows remote code execution inside its container, and container or host runtime is misconfigured such that the attacker can access host resources and other module containers. | - Harden container security: run all modules as non-root, drop unnecessary Linux capabilities, use read-only root filesystems, and restrict host volume mounts to the absolute minimum.<br>- Enforce container isolation using AppArmor/SELinux profiles and seccomp filters; prevent containers from using `--privileged` mode or host network namespaces in production.<br>- Separate modules onto distinct Docker networks and restrict inter-module access via network policies/firewall rules.<br>- Regularly scan container images and dependencies (SCA and vulnerability scanning) and patch known vulnerabilities in the web app and runtime components promptly.<br>- Use defensive coding practices in M1’s web app: strong input validation, parameterized queries, secure deserialization, and regular penetration testing focused on RCE vectors.<br>- Deploy host-based intrusion detection and monitoring (e.g., Azure Defender for IoT/Servers) to detect suspicious activity from containers and block lateral movement to host resources. |
| Elevation of Privilege | An attacker who obtains a high-privilege Azure Storage connection string from the Edge device uses it from an external environment to perform administrative operations on the storage account (e.g., create SAS tokens, modify access policies). | - Stop using high-privilege account keys on the Edge device; switch to Azure AD-based access with least-privilege roles (e.g., `Storage Blob Data Contributor` scoped only to required containers).<br>- If account keys must exist, restrict their use by IP (Storage firewall) and deploy only low-privilege keys to the device; store full-admin credentials only in secure management environments (Key Vault, admin workstations).<br>- Enable Azure Defender for Storage and monitoring on admin operations such as access policy changes, SAS generation, or key regeneration; alert on suspicious, off-hours, or geolocation-anomalous activity.<br>- Periodically rotate storage keys and revoke any keys suspected of exposure; ensure modules are designed to handle key rotation smoothly.<br>- Use resource locks and policy to prevent unauthorized modification of crucial access controls on the storage account. |
| Elevation of Privilege | SSO integration to M1 does not enforce fine-grained roles, and all authenticated users are treated as having administrative capabilities (e.g., triggering configuration changes, debugging modes, or forcing uploads to Azure Storage). | - Implement role-based access control (RBAC) in M1, distinguishing roles such as Viewer, Operator, and Administrator, with clearly defined, minimal privileges.<br>- Use IdP (Azure AD/other) group or claim-based authorization to assign roles; M1 should interpret these claims and enforce them consistently across all endpoints and UI actions.<br>- Restrict access to configuration-changing and debug-enabling functionality to administrator roles only; require MFA and possibly step-up authentication for such actions.<br>- Log all administrative operations with user identity, role, action details, and timestamps in an immutable audit log for accountability.<br>- Provide UI and API surfaces that expose only necessary controls to each role, limiting the chance of accidental or malicious misuse by normal users. |
| Elevation of Privilege | Inter-module communication on the IoT Edge device is not isolated by least-privilege rules, allowing a compromised low-privilege module (e.g., the Metrics Collector) to directly invoke privileged operations on M2/M3 or EdgeRuntime APIs. | - Design explicit, minimal APIs for inter-module communication: restrict which operations are exposed and require authentication/authorization tokens with scoped permissions for each calling module.<br>- Segment modules into separate virtual networks with firewall rules controlling which modules can talk to which endpoints and on which ports; deny-by-default for any unnecessary paths.<br>- Use distinct identities/credentials for each module; issue per-module tokens (e.g., JWTs or SAS) that embed the module’s identity and allowed scopes, and have M2/M3/EdgeRuntime enforce fine-grained authorization checks.<br>- Avoid giving “observer” modules (like metrics collectors) any credentials that allow state-changing operations; limit them to read-only telemetry interfaces where possible.<br>- Periodically review inter-module dependencies and ACLs to ensure they follow least privilege and reflect current architecture; remove outdated or unused interfaces that could be abused. |
