| Threat Type | Scenario | Suggested Mitigation(s) |
|-------------|----------|-------------------------|
| Spoofing | Credential stuffing or brute-force attacks against the basic username/password login on the Web UI to impersonate legitimate customers. | - Enforce strong password policy (length, complexity, block common/previously breached passwords).<br>- Implement MFA for customer accounts (TOTP or WebAuthn/FIDO2) and require it for sensitive operations.<br>- Add rate limiting and IP/user-based throttling on login and password reset endpoints (e.g., via WAF + app-level throttling).<br>- Implement account lockout or progressive backoff after several failed attempts, with secure out-of-band unlock mechanisms.<br>- Use modern password hashing (bcrypt/Argon2/PBKDF2 with per-user salt and high work factor) and never log raw passwords.<br>- Deploy credential stuffing protections (WAF bot rules, anomaly detection on login patterns, IP reputation).<br>- Monitor login failures and geolocation anomalies; alert on spikes or distributed attack signatures. |
| Spoofing | An attacker steals a valid session ID (e.g., via malware on the client, browser compromise, or XSS in the jQuery-based Web UI) and reuses it to pose as the victim. | - Use cryptographically strong, high-entropy, unpredictable session IDs; never include user-identifying data in the token itself unless signed (e.g., JWT with HS/RS algorithms).<br>- Mark cookies as `Secure`, `HttpOnly`, and `SameSite=Lax` or `Strict` where compatible.<br>- Bind sessions to context where possible (e.g., user agent fingerprint, IP range with care for mobile users; use as risk signal, not a hard requirement).<br>- Implement short idle and absolute session timeouts; require re-authentication or MFA for high-risk operations.<br>- Rotate session ID on login, privilege changes, and sensitive actions to reduce reuse window.<br>- Harden Web UI against XSS (CSP, input/output encoding, avoid unsafe jQuery patterns) to prevent session theft from the browser.<br>- Provide users the ability to view and revoke active sessions; invalidate server-side session state on logout or suspicion of compromise. |
| Spoofing | DNS poisoning or host file tampering on a client causes the Web UI to send credentials and session data to a malicious server that mimics the legitimate Web Service endpoint over HTTPS with a fraudulent certificate that the client accepts. | - Use valid TLS certificates from reputable CAs, with strong TLS configuration and HSTS enabled; preload where feasible.<br>- For controlled clients (mobile/desktop app, corporate environment), implement certificate pinning or CA pinning to your service certificates.<br>- Educate users to validate URLs and browser security indicators; avoid login flows that rely on redirects to unfamiliar domains.<br>- Use short-lived session tokens and MFA to reduce the value of stolen credentials.<br>- Monitor for typo-squatting and phishing domains; coordinate takedown where detected.<br>- Implement OAuth/OpenID Connect with well-known redirect URIs and CSRF protections to minimize credential exposure to spoofed endpoints. |
| Spoofing | The Web Service connects to a PostgreSQL endpoint whose hostname/IP is altered (e.g., DNS compromise or misconfiguration), causing it to send queries to an attacker-controlled PostgreSQL instance that impersonates the real RDS. | - Enforce TLS for all connections to PostgreSQL RDS using server certificate validation (e.g., verify RDS CA and expected hostnames).<br>- Configure the JDBC connection to require TLS and verify the server certificate chain and hostname (`sslmode=verify-full`).<br>- Use RDS-specific endpoints and restrict outbound network access so the Web Service can reach only the legitimate RDS subnet/security group.<br>- Lock down DNS in the VPC (e.g., Route 53) and prevent unapproved name servers or host file overrides on EC2 instances via configuration management.<br>- Store DB connection parameters in secure configuration (AWS Secrets Manager/Parameter Store) and avoid dynamic hostname overrides from untrusted sources.<br>- Monitor for connection attempts to unexpected DB endpoints and DNS changes via CloudTrail and VPC Flow Logs. |
| Tampering | An attacker submits crafted input (through the Web UI or direct XML API calls) that is not properly sanitized in the Java Web Service, resulting in SQL injection against the PostgreSQL RDS instance. | - Use ONLY parameterized queries/prepared statements or an ORM that safely binds parameters; prohibit dynamic SQL concatenation with untrusted input.<br>- Implement server-side input validation and canonicalization for all fields (type checks, length limits, whitelists where practical).<br>- Apply least privilege to DB accounts: separate app roles for read vs write vs admin; disallow DDL and superuser privileges for the Web Service role.<br>- Employ stored procedures where appropriate with controlled parameter lists, avoiding dynamic SQL inside them.<br>- Enable and tune WAF rules for SQL injection on Web UI and XML API endpoints.<br>- Regularly run SAST/DAST tools and security code reviews focused on data access layers.<br>- Configure PostgreSQL with restrictive `search_path` and set `statement_timeout` to reduce impact of injected long-running queries. |
| Tampering | XML requests from the client to the Web Service are altered in transit on a compromised client or proxy (e.g., changing parameters such as user IDs or transaction amounts) when the server does not validate authorization for each parameter. | - Treat all client-side data, including XML parameters and hidden fields, as untrusted; enforce authorization server-side for every sensitive field (object-level authorization).<br>- Use access control checks that verify resource ownership (e.g., user can only act on their own user ID or records) regardless of what ID is sent in the XML.<br>- Derive sensitive identifiers server-side from the authenticated session instead of trusting them from the request (e.g., ignore user ID parameter and use session user ID).<br>- Implement integrity checks for high-risk requests (e.g., server-generated nonces, signatures/MACs over parameters where appropriate).<br>- Ensure all communication is over TLS; consider mutual TLS for high-trust B2B API clients to reduce tampering risk in transit.<br>- Log full request context for sensitive operations for later forensic verification (redacting sensitive secrets). |
| Tampering | An attacker tampers with Web UI session cookies or session identifiers (e.g., by guessing or modifying them) if session IDs are predictable or not strongly random. | - Use a proven session management library that generates cryptographically secure random IDs with sufficient entropy (at least 128 bits).<br>- Do not encode privileges or trust decisions directly in client-side tokens unless cryptographically protected (e.g., signed JWT with validation and appropriate claims checks).<br>- Validate session tokens for integrity and format; reject malformed, expired, or unknown tokens server-side.<br>- Implement session fixation protections: issue new session IDs after login and significant privilege changes.<br>- Set `Secure`, `HttpOnly`, and `SameSite` flags on session cookies; avoid exposing session IDs in URLs or logs.<br>- Rate limit session validation attempts to reduce feasibility of brute-force token guessing. |
| Tampering | Compromise of the hosting location for the jQuery-based Web UI (e.g., S3 bucket, web server, or external CDN) allows an attacker to inject malicious JavaScript into the UI. | - Host Web UI assets in tightly secured S3 buckets or web servers with least-privilege IAM, no public write, and versioning enabled; disable direct public PUT/DELETE.<br>- Use a secure CI/CD pipeline for deploying UI assets (signed builds, restricted deploy roles, code review).<br>- Serve static assets via CloudFront with origin access control; do not allow direct public access to origins where not needed.<br>- Implement strong Content Security Policy (CSP) and Subresource Integrity (SRI) for scripts and styles to prevent loading tampered resources.<br>- Monitor integrity of static assets (e.g., checksums/hashes) and enable AWS CloudTrail for changes to S3 buckets or web server configs.<br>- Avoid including third-party scripts unless absolutely necessary; pin specific versions and verify integrity periodically. |
| Repudiation | A user performs sensitive operations (view, update, delete of confidential data) through the Web UI, but the Web Service logs only generic technical events (e.g., ‘update executed’) without tying them to authenticated user identities and session IDs. | - Implement structured audit logging at the Web Service layer that records: authenticated user ID, roles, session ID, client IP, timestamp (with NTP sync), operation type, target resource/record IDs, and success/failure.<br>- Design logging schema aligned with regulatory and business requirements (e.g., GDPR, PCI, SOX) and data minimization principles.<br>- Assign unique request IDs and propagate them through logs (Web UI → Web Service → DB) to correlate actions end-to-end.<br>- Provide tamper-evident, centralized log storage (e.g., CloudWatch Logs + S3 with Object Lock/WORM and restricted write-only roles).<br>- Regularly test log completeness and correctness (e.g., by replaying known actions and verifying they appear in the audit trail). |
| Repudiation | Administrative actions on the Web Service or PostgreSQL (e.g., configuration changes, schema changes) are not logged with sufficient detail or are stored in logs that can be altered by the same administrators. | - Enable and configure database auditing (e.g., PostgreSQL `log_statement`, `log_connections`, or an audit extension) to record admin commands and schema changes.<br>- Use separate, dedicated admin accounts with named identities (no shared admin accounts); require MFA for administrative access.<br>- Ship OS, Web Service, and DB logs to centralized, append-only logging (CloudWatch Logs/S3 with Object Lock and separate security account).<br>- Restrict log modification and deletion permissions; separate duties so DB/application admins cannot alter audit logs.<br>- Enable CloudTrail for AWS console/API actions, including RDS and IAM, and retain logs for an agreed retention period.<br>- Periodically review admin activity reports and configure alerts on high-risk administrative actions. |
| Repudiation | The system accepts XML requests directly to the Web Service API (bypassing the Web UI), but API clients are not uniquely identified and authenticated in logs beyond a source IP address. | - Require strong authentication for XML API clients (e.g., client certificates/mTLS, OAuth2 client credentials, or signed tokens) rather than relying on IP.<br>- Assign unique client IDs to each API consumer; include client ID and authenticated user identity (if applicable) in all log entries.<br>- Log API keys or client identifiers in a hashed/pseudonymous form to allow correlation without exposing secrets.<br>- Implement per-client rate limiting and quotas, and include client identity in monitoring and alerting dashboards.<br>- For B2B integrations, use strict allow-lists and separate IAM roles/credentials per partner. |
| Repudiation | Error handling in the Java Web Container is inconsistent, and some exceptions result in no logging or only partial logging of the triggering request and user context. | - Implement a centralized, global exception handler in the Web Service that catches and logs all unhandled exceptions with standardized fields (user ID, session ID, request ID, endpoint, parameters classification).<br>- Ensure that every HTTP response path (success, client error, server error) logs at an appropriate level (INFO/WARN/ERROR) without leaking sensitive data.<br>- Use structured logging (JSON) to capture metadata consistently and facilitate search and correlation.<br>- Regularly test error scenarios (chaos/failure injection) to confirm they produce complete logs and do not expose sensitive details to clients.<br>- Integrate error logs with alerting systems for repeated or suspicious failures (e.g., repeated auth failures, parser errors). |
| Information Disclosure | Improper XML parser configuration in the Web Service (e.g., allowing external entities) leads to XML External Entity (XXE) vulnerabilities when processing client XML input. | - Use XML parsers/configurations hardened against XXE: disable DTDs, external general/parameter entities, and external schema loading (e.g., set `FEATURE_SECURE_PROCESSING`, disable `ENTITY_RESOLVER`).<br>- Where possible, avoid XML entirely in favor of safer formats (e.g., JSON) for client-server communication.<br>- Apply strict input size, depth, and complexity limits on XML documents (parser features and application-level checks).<br>- Segment the Web Service from sensitive internal hosts; block access from the Web Service subnet to IMDS except via IMDSv2 and/or block the metadata IP at host firewall level.<br>- Conduct security testing (SAST/DAST) including XXE test cases for all XML endpoints.<br>- Keep XML libraries and frameworks up to date to pick up security fixes and secure-by-default configurations. |
| Information Disclosure | The Java Web Service or Web UI returns detailed stack traces or database error messages to clients over HTTPS when exceptions occur (e.g., SQL errors from PostgreSQL). | - Configure the Web Container and application to return generic, user-friendly error messages without stack traces or SQL details (e.g., standardized error codes).<br>- Log full exception details only server-side in secure logs (with care not to log secrets), not in responses.<br>- Map DB errors to sanitized business errors; avoid passing raw DB error strings into HTTP responses.<br>- Disable debug/error pages and verbose framework error handlers in production.<br>- Add tests to assert that common error conditions result in sanitized responses. |
| Information Disclosure | Authentication data, session IDs, or sensitive business parameters are logged in plaintext in Web Service or database logs for debugging or audit purposes. | - Implement a logging policy that explicitly forbids logging of secrets (passwords, tokens, session IDs, private keys, full PANs, etc.).<br>- Use centralized logging libraries or middleware that automatically redacts or hashes sensitive fields before logging (e.g., filter headers like `Authorization`, cookies, XML fields containing credentials).<br>- Review and sanitize existing log statements in the Java codebase and SQL logs to remove sensitive data.<br>- Encrypt logs at rest and in transit (CloudWatch Logs, S3 with KMS), and restrict access based on least privilege.<br>- Periodically scan logs for exposure of secrets using automated tools and rotate any credentials found. |
| Information Disclosure | TLS/HTTPS is enabled but not configured with modern best practices (e.g., weak ciphers still allowed, no HSTS, no certificate pinning on critical clients). | - Configure load balancers/Web Servers (e.g., ALB/NGINX) to support only strong TLS versions (TLS 1.2+ / 1.3) and secure cipher suites; disable SSLv3/TLS 1.0/1.1 and weak ciphers (RC4, 3DES).<br>- Enable HSTS with appropriate max-age and includeSubDomains; consider preload if domain strategy allows.<br>- Regularly rotate and manage certificates using AWS ACM or similar; monitor expiration and revocation status.<br>- For controlled clients (mobile, rich clients), implement certificate/PKI pinning to your CA or certificate key.<br>- Use modern TLS for DB connections (RDS enforced TLS) and internal services as well, not only public endpoints.<br>- Periodically scan endpoints with TLS assessment tools and remediate findings. |
| Denial of Service | An attacker sends very large or deeply nested XML payloads (XML bombs) to the Web Service, overwhelming XML parsing resources (CPU, memory) on the Java Web Container. | - Configure XML parsers with strict limits: maximum document size, maximum depth, entity expansion disabled, and limits on number of attributes/elements.<br>- Implement request size limits at the web server/load balancer (e.g., ALB/NGINX `client_max_body_size`) and WAF (max body inspection size).<br>- Apply timeouts and resource limits around parsing operations (e.g., parse in bounded thread pools with timeouts and circuit breakers).<br>- Use streaming XML parsing (StAX) where possible instead of DOM to reduce memory footprint.<br>- Add rate limiting per IP/API key for XML endpoints and monitor for abnormal XML error rates. |
| Denial of Service | Flooding the basic authentication endpoint with high-volume login attempts or automated session creation requests, exploiting any lack of rate limiting or CAPTCHA. | - Implement IP and account-based rate limiting for login and session-creation endpoints at both WAF and application layers.<br>- Introduce CAPTCHAs, proof-of-work, or other bot mitigation for excessive or suspicious login activity.<br>- Use exponential backoff and temporary lockouts after repeated failed attempts, combined with safe user notifications.<br>- Offload authentication to a scalable identity provider (IdP) where appropriate, leveraging its built-in throttling and anomaly detection.<br>- Monitor login endpoint metrics (requests/sec, failures/sec) and configure alerts for spikes indicative of attack traffic. |
| Denial of Service | Crafted requests from the Web UI or direct clients trigger expensive database operations (e.g., unbounded queries, complex joins) on PostgreSQL via the Web Service. | - Enforce server-side query constraints: mandatory pagination, maximum page size, and limits on sorting/filtering options.<br>- Review and optimize queries; add indexes and avoid unbounded `SELECT *` / full table scans from user-controllable parameters.<br>- Introduce application-level guards that detect and block obviously abusive parameter combinations (e.g., huge date ranges, wildcards across large datasets).<br>- Set PostgreSQL resource limits (`statement_timeout`, `work_mem`, connection limits) to mitigate long-running or concurrent heavy queries.<br>- Use read replicas or caching for heavy read workloads; isolate analytical/reporting queries from transactional workloads where possible.<br>- Monitor slow query logs and DB performance metrics; tune or refactor problematic endpoints. |
| Denial of Service | Network-level attacks from the Internet (e.g., SYN floods, HTTP floods) target the public-facing Web UI or Web Service endpoints, and there is insufficient upstream protection (e.g., WAF, DDoS mitigation). | - Place the Web UI and Web Service behind a managed DDoS protection service (e.g., AWS Shield / Shield Advanced + CloudFront/ALB).<br>- Deploy and tune a WAF (AWS WAF) with rules for rate limiting, IP reputation, and application-layer attack patterns (HTTP floods, malformed requests).<br>- Implement autoscaling for Web Service EC2 instances behind an ALB to absorb volumetric surges where feasible.<br>- Use connection-level protections (SYN cookies, connection limits) on front-end load balancers or gateways.<br>- Separate public and administrative interfaces; restrict admin access via VPN, private subnets, and security groups.<br>- Regularly perform DDoS readiness reviews and run simulations to validate runbooks and capacity. |
| Elevation of Privilege | The Web Service exposes endpoints intended for administrative tasks (e.g., user management, configuration) that are not properly access-controlled and can be invoked by authenticated but non-admin users via direct HTTP/XML calls. | - Implement strict, server-side role-based access control (RBAC) or attribute-based access control (ABAC) for every admin endpoint; enforce checks on the server, not the client.<br>- Group and isolate admin functionality under separate URL namespaces and services; require explicit admin roles and, ideally, MFA for access.<br>- Avoid security-by-obscurity (e.g., hidden URLs); assume endpoints are discoverable and protect them with robust authorization checks.<br>- Conduct periodic access reviews and penetration tests focused on privilege escalation via hidden or misconfigured endpoints.<br>- Log all administrative endpoint access with user ID, roles, operation details, and success/failure for audit. |
| Elevation of Privilege | The jQuery Web UI relies on client-side checks (e.g., hiding admin buttons or sending a role parameter from the browser) without robust server-side authorization in the Web Service. | - Treat the Web UI as untrusted: remove reliance on client-side role parameters or UI visibility as a security control.<br>- Enforce authorization centrally in the Web Service for each action, regardless of UI behavior; ignore client-supplied role claims unless cryptographically verifiable.<br>- Do not send capabilities to the client that the user is not allowed to exercise (e.g., avoid exposing admin-only endpoints in JavaScript unless needed, and still enforce server checks).<br>- Implement tests to ensure that unauthorized users cannot perform admin actions via direct HTTP/XML calls, even if they manipulate requests manually.<br>- Provide separate, hardened admin interfaces with their own access policies and monitoring. |
| Elevation of Privilege | The Java Web Container or application uses libraries or frameworks that accept serialized objects or complex XML structures from clients; insufficient validation leads to remote code execution or arbitrary method invocation on the Web Service host. | - Eliminate Java native deserialization of untrusted data wherever possible; use safer formats (JSON, simple XML) and explicit parsing instead.<br>- If deserialization is unavoidable, implement allow-lists of permitted classes, and use hardened libraries that restrict gadget chains.<br>- Keep all libraries, frameworks, and the Java runtime up to date with security patches, especially those related to serialization/XML handling.<br>- Run the Web Service under a minimally privileged OS account; apply OS-level hardening (AppArmor/SELinux, no unnecessary sudo/root rights).<br>- Use a WAF to detect and block known deserialization exploit patterns where possible.<br>- Conduct regular dependency scanning (SCA) and code reviews focusing on deserialization and reflection usage. |
| Elevation of Privilege | The IAM role or credentials used by the Web Service EC2 instance to access PostgreSQL RDS also grant broader access to other AWS services (e.g., S3, KMS, IAM) than required. | - Apply strict least-privilege to the EC2 instance role: grant only the permissions required for normal Web Service and DB operations.<br>- Split duties using multiple IAM roles for different components (Web UI hosting, Web Service, batch jobs) rather than a single, overprivileged role.<br>- Use IAM Access Analyzer and CloudTrail to identify and reduce unused or overly broad permissions.<br>- Restrict high-impact AWS actions (IAM changes, KMS key management, S3-wide access) to dedicated admin roles with MFA, not to application roles.<br>- Limit access to Secrets Manager/Parameter Store so the Web Service can retrieve only necessary secrets, with resource-level permissions.<br>- Regularly review and re-certify IAM role policies as part of security governance. |
